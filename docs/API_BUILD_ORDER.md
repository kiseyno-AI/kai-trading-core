## External news notes

- `GET /external/news/health` reports the configured collection provider's `provider`, `enabled`, `status`, and `reason` without fetching news. `POST /external/news/collect` requires a comma-separated `symbols` query, accepts `display=1..100` with a default of `10`, returns a normal `status="disabled"` payload when collection credentials are unavailable, and reports symbols that are not in the symbol master as per-item skips. `GET /external/news` is the current persisted operator read; it accepts an optional comma-separated `symbols` filter and `limit=1..1000` with a default of `100`.
- External-news article observations are immutable. Repeated collection may add a first-known symbol association in `external_news_item_symbols`, while classification changes append a timestamped row in `external_news_item_classifications`; neither path rewrites the original article observation. The current operator read exposes `associated_at` plus the latest sidecar's `classification_provenance`, and exposes classification fields only when that selected sidecar satisfies the schema contract.
- Point-in-time consumers must use `GET /agent-context/symbol-day`, not the direct current read. Its exclusive `knowledge_cutoff_at` bounds publication, collection, first-known symbol association, and selected classification observation timestamps with strict `<` semantics, and its lookback is anchored to that cutoff. Historical context selects the latest sidecar strictly before the cutoff and exposes it only when schema-valid; that sidecar may use an older classifier version. EOD `external_news_enrich` readiness separately requires the current `CLASSIFIER_VERSION` and full classification schema.

## Agent context notes
- `GET /agent-context/signal-decider/calibration` now includes a backward-compatible `rule_candidates` section. Candidates are deterministic, structured, replay-only proposals from negative calibration clusters; they default to `activation_status="needs_replay"` and are not active policy.
- `POST /agent-context/signal-decider/weekly-learning/publish` persists an immutable, content-hashed weekly artifact from verified calibration evidence plus economically eligible actual execution outcomes. The requested week is an audit/evidence window; training uses a 90-day rolling cohort ending before `max(14, 3 * horizon_days)` calendar days so pending h5 decisions do not poison coverage. The versioned Exec manifest must carry `weekly-learning-quality/v1`: Core derives performance eligibility from complete cost-basis, transaction-cost, settlement-currency, fill-attribution, and closed-trade-lineage coverage, and derives failure eligibility from normalized failure counts with complete failure lineage. Compact status/eligibility booleans cannot override incomplete evidence. A week with no closed trades, execution failures, or terminal order outcomes may publish only as explicit `calibration_only`; these artifacts label that realized-execution learning is not included. Missing, malformed, or contradictory quality contracts fail request validation; structurally valid ineligible evidence is stored only as `ineligible` audit history. Stable manifest idempotency keys ignore retry-only run metadata, while the complete accepted manifest remains auditable and same-identity quality drift is rejected as an idempotency conflict.
- `GET /agent-context/signal-decider/weekly-learning/latest` returns only the newest published, eligible, hash-valid artifact applicable to the requested date. Within an exact evidence week and source identity, a newer valid correction supersedes the older immutable row; an ineligible correction makes that guidance unavailable to latest/context reads until a later eligible correction reaches its normal effective date. Artifacts expire 14 days after the evidence week; a newly published stale backfill cannot shadow a still-valid current artifact. Explicit historical reads require the artifact to be effective strictly after both its evidence week and publication date, preventing future learning from leaking into old decision revalidation. Fresh artifacts replace the live rolling performance criteria under the existing `signal_decider_policy.performance_criteria` contract for both deciders. Signal-decider falls back to the existing rolling calibration when no artifact is available, short-term-decider preserves its previous empty policy context, and neither path submits orders or activates policy changes.
- Calibration responses now expose descriptive `group_summaries.outcome_path_buckets` and `group_summaries.reward_risk_buckets` sections with the same bucket-stat shape as other summaries. These outcome-derived buckets are reporting-only and are intentionally excluded from `condition_clusters` and `rule_candidates[*].predicate.conditions` because they are only known after replay maturity.
- `GET /agent-context/symbol-day` now includes a compact `factor_summary` block plus a compact `liquidity_context` block for prompt-safe decider use.
- `liquidity_context.turnover.status` distinguishes `available`, `derived`, `stale`, `missing_price_or_volume`, and `storage_unavailable` so deciders can tell current-day turnover, safe close×volume fallback, stale prior-day context, and true storage failures apart.
- `liquidity_context.turnover` now also carries `trading_value_source` (`raw`, `estimated`, or `missing`). Raw PyKRX/KRX `valuation_snapshot.trading_value` is preferred over close×volume estimates when present, and estimated fallback is labeled explicitly.
- `liquidity_context` also carries low-risk liquidity ranking fields when available and intraday KIS quote/orderbook freshness hints without requiring deciders to parse the full rich `price_context` and `intraday_execution_context` blocks.
- Each symbol item now includes `pre_decider_enrichment_context`, a compact handoff block for `quote_orderbook_snapshot`, `trading_value`, and `flow_short_sector_context`. It joins quote/spread/orderbook/execution-strength hints, raw-or-estimated trading value provenance, investor flow, short-selling, market breadth, and sector peer context before `signal-decider` or `short-term-decider` dispatch.
- Each symbol item and decider request payload now include `market_regime_context`, a deterministic core-owned market/sector posture contract for buy decisions. It combines sector/category peer context, market-relative strength, fresh same-date KIS index/open/breadth/cumulative-value evidence, and macro FX context when available into `posture` plus `market_regime` (`defensive`, `normal`, `aggressive_open`, or `trend_day`). KIS intraday-bar business date/time—not cache attempt time—is the index observation. `prdy_tr_pbmn` is the preferred same-provider prior-session turnover; the PyKRX fallback accepts only a completed zero-failure EOD run with complete as-of-universe metadata, exact symbol-set coverage, and matching requested/persisted membership SHA-256 digests. All five breadth buckets remain raw in the snapshot, while strong breadth additionally requires a completed same-date KIS-master universe and a total that resolves limit-bucket semantics. Missing/timeout fallback preserves the index leg but cannot confirm value expansion. The conservative minimum 25% elapsed-session denominator is audited and no linear full-day projection or last-known fallback is used. Uncalibrated aggressive/trend multipliers and confidence uplifts are exposed only as `shadow_quantity_multiplier` / `shadow_regime_confidence`; live `quantity_multiplier` and sizing-window cap remain at 1.0 with entry-priority boost disabled.
- Each symbol item now includes `decision_input_quality_context`, a reusable buy-quality / quality-provenance envelope layered over `decider_data_quality_context` and `pre_decider_enrichment_context`. It separates data quality, market/setup edge, execution feasibility, and final judgment; stale/fallback quote evidence and missing raw source turnover are surfaced as hard blocks or major discounts, while empty news/disclosure context is neutral secondary context. The envelope uses a free/current-data-only policy (`paid_api_dependency=false`): incomplete PyKRX/KRX/KIS/DART/local data is represented as explicit missingness/provenance plus conservative gates rather than a requirement for paid data APIs.
- Each symbol item and the `signal-decider` request payload now include `macro_context`, a compact slow-moving macro backdrop with source statuses, freshness metadata, and deterministic `macro_regime_summary` labels. It is contextual input only, not a direct buy/sell signal, and no LLM is used to generate the regime labels.
- Missing requested-date `quote_context`, `intraday_execution_context`, and provider-backed optional PyKRX blocks now remain structured objects with explicit `status`, `reason`, and `freshness_provenance` instead of raw `null`, so deciders can tell unavailable/not-collected/stale states apart from omitted payload fields.
- Symbol-day responses now also expose a top-level `market_session` block and repeat it under `summary.market_session` and each item's `market_session`. The metadata keeps the requested calendar date, current calendar date, latest valid trading date, market-session status, data-expected flags, and recommendation basis explicit for weekend, holiday, pre-open, after-close, and historical-trading-day reads.
- Each symbol item and `pre_decider_enrichment_context` now also expose `market_data_phase_contract`. ## Next-open execution planning notes
- `GET /trading/orders/next-open-execution` is the persisted inspection surface for the next-session buy list derived from the latest previous-trading-day decision snapshots. It includes classic `signal-decider` next-open buys plus `short-term-decider` tactical rows with explicit per-row decider identity. `scalp_buy_candidate` rows can be buy-eligible; `watch_for_trigger` rows are monitor-only and return `eligibility_status="monitor_candidate"` with `execution_status="awaiting_trigger"` until their trigger conditions are satisfied. `refresh=true` rebuilds the durable plan before returning it.
- Feedback observed after the target KRX open cannot create retrospective next-open market-order authority. During that same target date's live `OPEN` session only, a fresh wait-recheck result may materialize either a `short-term-decider` `watch_for_trigger` or a `signal-decider` BUY with `entry_price_basis=trigger_limit` as a trigger-gated `intraday_watch_buy`; its validation and traceability carry `decision_authority.scope="same_day_intraday_watch"`, `trigger_gated=true`, and `market_order_authority=false`. Unsolicited late signal-decider BUYs, signal BUYs that still use `next_open`, `scalp_buy_candidate` decisions, PREOPEN/CLOSED sessions, and later dates remain tombstoned. This exception does not relax live quote freshness, trigger/chase validation, account/portfolio risk, kill switch, or live market risk-off gates.
- With `SIGNAL_DECIDER_WAIT_RECHECK_MONITORING_ENABLED=true`, the realtime subscription source may append a bounded low-priority partition of prior-session WAIT rows from both decision lanes whose latest durable snapshot has one explicit lane-specific upgrade (`signal-decider` -> `buy`, `short-term-decider` -> `watch_for_trigger`) plus coherent trigger/chase/target/stop geometry. A fresh subscribed KRX regular-session best ask at or above the trigger and below the target and chase cap persists one `(target_trade_date, symbol, agent_name)` event and requests one fresh computation from that exact agent. The immutable event context explicitly has no order authority and is accepted only while its hash, identity, source-snapshot lineage, trigger geometry, observed prices, quote provenance, and timestamps exactly match both the durable event and actual source snapshot. Only a terminal newly computed lane-appropriate action may be consumed by the existing same-day intraday-watch planner; WAIT/reject creates no plan, and other late results retain the existing expiry rules. Claimed, expired, or removed WAIT symbols are authoritatively removed from their own subscription partition even when the Exec membership source is partial, so they cannot accumulate ahead of current candidates.
- `POST /trading/orders/next-open-execution/run-if-due` is the operator-facing hook used by the background runner at market open. In `SIGNAL_DECIDER_EXEC_INTEGRATION_MODE=disabled`, it still refreshes and exposes the compatibility plan, but signal-decider buys remain blocked because Core does not perform an execution-time quote/cost recheck; source-day evidence cannot select a row for submission or dry-run. `short-term-decider` rows likewise remain inspection-only in core-local mode because trigger/chase semantics are not translated into local market orders. In `dispatch` mode the route translates buy-eligible rows and monitor-only watcher rows into normalized Exec plan items and delegates sizing/execution authority to `kai-trading-exec`.
- The background runner gives the single-flight next-open plan refresh 120 seconds, independently of the 45-second default for ordinary blocking steps. Source validation, PyKRX inspection, live-market refresh, and legacy authority recovery can legitimately exceed 45 seconds; the longer bound avoids a false degraded tick while the single-flight task still prevents overlap.
- Next-open summaries distinguish immediate buy eligibility from monitor readiness: `buy_eligible_count` aliases `eligible_count`, `monitor_candidate_count` counts monitor-only rows, `awaiting_trigger_count` counts rows waiting for a trigger, and `ready_count` is `eligible_count + monitor_candidate_count`. Consumers must not treat `monitor_candidate_count` or `ready_count` as immediately buy-eligible quantities.
- Requested next-open target dates are normalized to the next KRX open date on or after the request date. KIS `chk-holiday` (`CTCA0903R`) `opnd_yn` is authoritative when available, so holidays and other KRX non-open dates roll forward instead of planning against a closed session.
- Local live next-open submission, intraday auto-sell submission, and exec dispatch fail closed when market-calendar truth is only available through fallback metadata; `force=true` is the explicit operator override for those paths.
- Durable plan rows live in `signal_decider_execution_plan_items` and now link one `decision_snapshot_id` to one concrete `account_reference + target_trade_date + symbol + decision_agent_name` execution candidate, plus optional `order_request_id` and `broker_order_row_id` once submission starts. Each row also carries explicit source identity in validation/traceability state, including `decision_agent_name`, `decision_run_id`, `source_feedback_id`, `source_market_date`, and `target_trade_date`.
- Next-open validation and traceability now preserve the decider request's `pre_decider_enrichment_context` for `short-term-decider` rows, so operators can inspect the exact quote/orderbook, trading-value, investor/short, and sector-peer context that guarded dispatch.
- Short-term validation and traceability preserve signal-decider alignment audit fields, but dispatch runtime keeps the signal and short-term lanes independent. `SIGNAL_DECIDER_WAIT_CONFLICT_GATE_MODE=report_only` records disagreement without changing short-term eligibility or quantity, and `disabled` omits enforcement. Settings validation rejects `hard_block` and `downsize_probe` whenever `SIGNAL_DECIDER_EXEC_INTEGRATION_MODE=dispatch`; those modes are observe/offline replay tools only. Shared account/symbol exposure, quality, pause, and kill-switch gates still apply across both lanes. The internal weekly replay covers at least four completed KST week windows using actual fills/outcomes only, applies one requested replay probe quantity across all historical rows, counts only full weeks with resolved replay evidence toward promotion, weights downsize tradeoffs by removed quantity, and separates unresolved/open candidates. See `docs/WAIT_CONFLICT_GATE_ENFORCEMENT.md` for thresholds and limitations.
- Next-open validation and traceability now preserve `market_regime_context` and `decision_input_quality_context` for both `signal-decider` and `short-term-decider` rows. The regime context keeps market/sector posture, freshness, recommended exec action, and sizing multiplier visible for kiseyno-AI/kai-trading-exec#140; the quality envelope keeps missing-data penalties, positive confirmations, execution-feasibility score, liquidity tier, max safe notional, and sizing hints visible without changing deterministic live-dispatch authority.
- Compatibility quantity planning remains explicit and account-scoped when `SIGNAL_DECIDER_EXEC_INTEGRATION_MODE=disabled`, but a planned quantity is not buy authority and current signal-decider next-open rows fail the missing execution-time cost gate. `SIGNAL_DECIDER_NEXT_OPEN_ACCOUNT_TARGETS` maps account references to KRW budget rails in `Label=KIS:12345678-01@1500000` form; in dispatch mode those rails are sizing/risk context for Exec rather than fixed-share authority.
- Classic `signal-decider` and actionable `short-term-decider` candidates are treated as candidate/exec-agent flows in dispatch mode (`quantity_policy.type='exec_agent_sized'`) and carry account budget, reference/entry, confidence, target/stop, risk, and source traceability context instead of precomputed fixed share quantities. Accepted rows without an agent-provided positive quantity are classified as `delegated_for_exec_agent_sizing`, not as locally executable core buys. General `signal-decider` handoffs explicitly opt out of the short-term default max-holding forced close policy; only `short-term-decider` handoffs carry the 3-trading-session `max_holding_close_sell` default for exec-agent monitoring.
- Exec handoff payloads now carry `risk_context.decider_handoff_context` for each planned item, including execution-relevant decider request context, input feature snapshot payload, pre-decider enrichment context, filtered response payload/summary, normalized tactical fields, risk/data-quality warnings, and source traceability (`feedback_id`, `decision_snapshot_id`, `decision_run_id`, and core plan item id).
- Exec handoff payloads carry market-regime, decision-quality, execution-feasibility, and alignment context. Delegated-gate authority exists only on each buy item's top-level `risk_context`: `delegated_gate_codes`, `delegated_gate_confirmation_required`, and structured `delegated_gates`. Codes and structured entries have exact matching order/cardinality, and each gate has exactly nine keys: code, observed value/path/time, comparator, threshold, policy version, recheck source, and expiry. Naive, future, expired, missing, extra, or non-allowlisted gate metadata fails before the Exec POST. Those fields are omitted from nested traceability and linked protective sells. Compact payloads preserve all structured gate keys, including an explicitly present `observed_value=null` for pending live cost. Exec-agent-sized buy `quantity_policy` includes sizing/liquidity and capped market-regime hints; no hint bypasses kill switch, drawdown, symbol/notional caps, or stop-loss requirements.
- Accepted Exec authority persists an immutable per-item proof binding `core_item_key`, `execution_plan_id`, and `execution_plan_item_id` from the validated ACK. Plan readback may update status only for that exact tuple; a core-key, plan-ID, or item-ID mismatch is discarded and audited as `exec_readback_identity_mismatch`, preserving the original IDs for revocation.
- Before next-open planning or exec dispatch proceeds for a source market date, Core checks PyKRX enrichment coverage for `sector_classification`, `investor_flow_symbol`, `short_selling`, and `valuation_snapshot`. The first three require at least 99% expected coverage; direct same-day PyKRX valuation rows require at least 95% of the supported KOSPI/KOSDAQ universe, a positive market cap, and at least one valuation metric. Missing or below-threshold coverage blocks classic `signal-decider` immediate next-open buys with `reason="pykrx_enrichment_preflight_blocked"` and exposes `enrichment_preflight_status`, `enrichment_failed_categories`, and the full `enrichment_preflight` payload in next-open responses. Actionable `short-term-decider` watch candidates are still materialized as visible conditional rows when their candidate-level trigger/chase fields exist; the preflight failure is attached as warning/degraded metadata instead of erasing the candidate list. `force=true` is an explicit operator bypass.
- Next-open plan refresh/list responses include `agent_context_completeness` plus compact summary fields (`agent_context_completeness_status`, `agent_context_incomplete`, and `agent_context_failure_count`). Completeness is anchored to the latest durable retry-cycle parent cohort, including full five-role workflows that contain both deciders. A versioned `child_run_lineage` marker makes only children whose durable request carries that parent's `parent_run_id` authoritative. A late child from an older parent is ignored, and an abandoned or stale-running newer parent or child blocks fallback to an older BUY cohort. Equal start times use the durable row id as the final ordering key. Versioned reuse requires the exact role/symbol plus structured `reused_feedback_evidence_by_role` provenance (`feedback_run_id`, `feedback_received_at`, available `feedback_id`, and immutable `decision_snapshot_id` or content fingerprint with optional observed time). The evidence must resolve to the immutable snapshot actually selected by the immediately preceding applicable parent; mutable feedback-receipt updates and older-parent or older-sibling callbacks therefore fail closed. Snapshot creation time is only a fallback for non-versioned legacy rows whose receipt is null. Otherwise a requested result with no new snapshot is a tombstone and cannot leak an older BUY. Candidate-scope `incomplete`, `unknown`, or unavailable evidence blocks planning. Each plan row stores its candidate-specific authority fingerprint, so an incomplete symbol does not suppress a separately complete symbol; the response-level cohort can still be `candidate_set_definitive=false` with `agent_context_source_cohort_incomplete`. The fingerprint/status is rechecked under the refresh lock, for terminal handoffs, and immediately before Exec dispatch. Dispatch generation hashes only row-scoped decision authority, so unrelated symbol or summarizer checkpoints cannot revoke a valid handoff; stale BUY authority still moves to revocation or blocked state. Upstream summarizer freshness invalidates both signal-decider and short-term-decider reuse, and a newer failure always keeps that role pending for retry.
- Monitor-only `intraday_watch_buy` authority is stable across ordinary live-market snapshot ticks. Core still synchronizes every live risk-off observation to Exec's buy fence, but the observation timestamp and breadth are excluded from the monitor row and dispatch-generation fingerprints because they govern later order submission rather than membership in the watch set. A legacy monitor plan incorrectly revoked only by this generation drift may be re-created automatically after Core verifies the exact accepted plan/item links, unchanged row revision, ACKed remote revocation, unchanged decision/policy/agent authority, and the current market-date fence state. Stale or unavailable market evidence may restore watch membership but remains `block_new_buy` at Exec. This compatibility recovery restores monitoring only; it never clears the Exec buy fence or grants order authority.
- Safety rails are separate from decider prompt contracts. Buy return and reward/risk use cost amount consistently: cost reduces reward and increases loss. Quote-spread evidence is labeled `slippage_adjusted`, not net, and is admitted only from an executable snapshot with exact status/type, same-market-date provider provenance, and a timezone-aware timestamp no older than `KIS_REALTIME_PRICE_STALE_AFTER_SECONDS` (default `30`). Provider table names must equal the exact selected quote or intraday set, with no extras/duplicates, and price/bid/ask/spread components must come from one source context and form a positive coherent book. Completed-EOD prices may supply recommendation/reference geometry, but an EOD spread is never current execution-cost evidence. Missing, fake-zero, invalid, stale, future-dated, date-mismatched, mixed-source, non-finite, or non-canonical evidence fails closed. A canonical completed-EOD shape may become `pending_live_cost_confirmation` only in Exec dispatch: Core uses gross geometry for pre-screening, emits the delegated live-cost gate, and grants no direct execution authority; Exec must recheck live liquidity/price/cost and enforce its final full-cost gate. Core-local signal-decider next-open buys remain blocked because the path has no execution-time quote recheck; its server-owned `SIGNAL_DECIDER_NEXT_OPEN_NON_SPREAD_ROUND_TRIP_COST_BPS` allowance (default `50`) is additive and cannot replace spread evidence. Only short-lived liquidity (`>= 3B KRW`) and reward/risk (`>= 1.80`) watch failures are delegable; quality/ATR/trend/relative-strength failures stay blocked in Core.
- Active non-terminal pre-open rows are revalidated on every scheduler tick against current KRX-scoped snapshots, corrected daily bars, enrichment, policy state, and account routing. `next_open_preopen_policy_v1` records the integration mode, cost-evidence contract version, non-spread allowance, confidence/expected-return/reward-risk thresholds, and exact account label/reference/budget as audit evidence; it does not authorize reuse of stale eligibility. Already-terminal dispatch/submission history is not rewritten.
- If a persisted candidate still exists but fails the durable decision-input generation check, plan refresh reports `decision_input_generation_changed`; `candidate_removed` is reserved for a genuinely absent latest candidate. Both states fail closed, but the distinct reason keeps recovery and operator diagnosis accurate.
- Active-watch feedback inclusion is one-way across source dates: only `eligible`/`monitor_candidate` plan rows from an earlier source market date may force inclusion. Blocked rows and same-source-date rows are downstream outputs and are excluded, preventing a newly materialized plan from changing the decision-input fingerprint that created it.
- Snapshot cohort reconstruction first projects immutable identity/lineage timestamps for the full source-date scope and hydrates complete decision payloads only for the selected IDs in the same transaction. Feedback-run request/summary documents are selected once per row and immediately reduced to the existing authority whitelist in Python, instead of repeatedly extracting and detoasting the same JSON in SQL. Missing rows or any projection-to-hydration authority-token drift fails closed, while historical unselected snapshot JSON/TOAST payloads are not loaded by the dispatch fence.
- In dispatch mode an ordinary eligible `signal-decider` row with `entry_price_basis=next_open` becomes one `next_open_buy` exec item plus linked `target_sell` and `stop_sell` monitors. A freshly promoted signal row with `entry_price_basis=trigger_limit`, and each actionable `short-term-decider` watch row, instead dispatches as `intraday_watch_buy` with its trigger and chase cap preserved; there is no next-open market fallback. Immediately before handoff, signal trigger rows must still be `limit` / `monitor_candidate` with active intraday handoff, `pending_trigger_limit`, and trigger/chase/target/stop values exactly matching the immutable snapshot, or Core records a contract error and sends nothing. Core groups items by `account_reference + decision_agent_name`, sends stable decider-aware `plan_id` / `strategy_run_id` / idempotency material, and persists per-row linkage or audit state under `signal_decider_execution_plan_items.submission_payload.exec_dispatch`.
- Exec readback now repairs stale intraday-watch display state for either decision agent without creating broker orders. If Exec reports an accepted, active, pending, or submitted watch entry for a matching buy row that Core still has as `blocked/planned`, Core updates `execution_status` to `delegated_for_exec_agent_sizing`, preserves the original validation `blocking_reasons` and warnings, stores `exec_watch_state_sync` audit metadata, and surfaces `core_state_divergence_warning` plus summary divergence counts in exec overview/dashboard read models.
- If `SIGNAL_DECIDER_NEXT_OPEN_ACCOUNT_TARGETS` is empty, short-term rows remain visible through a synthetic placeholder rail (`UNSPECIFIED_ROUTE`, `KIS:00000000-00`) instead of being dropped. That placeholder is monitor-only in live runtime and may dispatch only in mock/paper runtime. Live Exec dispatch requires exactly one explicit valid KIS account target and exact row-to-target binding; missing, invalid, multiple, mismatched, or synthetic routes fail before HTTP with `live_exec_account_target_required`.

## Core to exec integration notes
- `SIGNAL_DECIDER_EXEC_INTEGRATION_MODE` controls the integration lane. `disabled` keeps the Core-local compatibility/read path but cannot authorize signal-decider next-open buys without an execution-time quote/cost recheck; `observe` adds runtime/readback inspection without gaining execution authority; `dispatch` delegates automated next-open execution and buy sizing to Exec while keeping dashboard-facing aggregation in Core. The delegated set includes classic `signal-decider` rows plus actionable `short-term-decider` tactical rows.
- Execution handoff and runtime read-model fields are owned by the executable contract in [apps/api/app/orders/execution_handoff_contract.py](../apps/api/app/orders/execution_handoff_contract.py). This checklist records route availability only; dispatch payload, runtime status, dashboard read-model, today-activity, and portfolio-equivalent field/status drift should be changed in code and locked by contract tests first.
- OPEN dispatch additionally requires a route-wide `current_live_market_buy_authority_v1` observation built only from fresh authoritative KOSPI and KOSDAQ market evidence. Core persists the exact KIS/KRX/KRW runtime/account authority state and pending outbox row atomically, then calls Exec `POST /runtime/core-buy-authority/observations` before any v4 buy. The candidate-empty route still sends an observation when both required markets are authoritative; missing or stale market truth produces an explicit block instead of a healthy observation.
- The authority payload uses a canonical material fingerprint and idempotent observation ID. Exec applies it as a scoped durable two-phase fence and ACKs only after plan-item projection settles. Core may dispatch only when the exact latest ACK reports `fence_active=false` and `projection_pending=false`; delivery uncertainty, mismatched/stale/conflicting IDs, interrupted projection, or a duplicate pretending to be new healthy evidence all fail closed. Recovery releases only the scoped market-authority fence or drawdown latch and never resumes the whole runtime, clears another risk-off control, or revives an old order; every new candidate runs all current gates.
- Exec-owned US account proof remains conservative in Core readback: every non-zero holding needs a known non-negative valuation and every open buy needs a positive-price notional. Legacy cumulative fills without explicit `fill_time_precision` are treated as `observed_upper_bound` and block US buys until an exact-scope verified-flat boundary. Duplicate fill IDs whose quantity, base/quote notional, price, settlement currency, transaction cost, coverage, source, or currency-conflict evidence disagree are excluded from P/L and block US buys. Shared KIS token-lock timeouts are bounded and retryable (`503`, `TRANSIENT`, `RETRY_PENDING`); neither service may bypass the shared lease, issue an uncoordinated token, or replay the failed broker request.
- Core preserves exec-owned runtime summary dictionaries from `/runtime/status` for dashboard consumption, including `symbols`, `daily_pnl`, `weekly_pnl`, `monthly_pnl`, and `actionable_alerts`. Core normalizes current autonomous liveness from `liveness.autonomous.monitoring`, and `pnl_coverage` reports `available` or `unavailable` plus a period-specific `status_reason` when Exec omits or cannot compute P/L. Core validates envelope shape and connection state, but it does not recompute FIFO P/L or sell coverage fields that Exec owns.
- Ownership is explicit: Core owns strategy planning, dispatch payload construction, cached dashboard read models, and the portfolio summary equivalent; `kai-trading-exec` owns execution truth, order/execution/position readback, pause, kill switch, and runtime liveness; Web consumes Core payloads for display only and must not infer or submit execution commands from these routes.
- `GET /trading/orders/exec/runtime` is the explicit operator read for exec readiness. It surfaces `disabled`, `not_configured`, `unavailable`, and `contract_error` states directly so operators can tell configuration failure apart from transient runtime failure.
- `GET /trading/orders/exec/signal-decider` is the core-owned aggregated read model over persisted decider-aware next-open plan rows plus exec runtime/order/execution/position readback. The route name is legacy, but the payload now includes both `signal-decider` and actionable `short-term-decider` entries, explicit per-item decider identity, raw tactical action, generic action, handoff intent, approval state, active monitoring state, and tactical trigger/chase fields where applicable. `refresh=true` calls the exec northbound APIs, persists the latest matched readback snapshot onto the durable next-open plan rows, and returns planned-vs-actual operator items without requiring web clients to query exec directly.
- Exec v4 `item_acks` are immutable acceptance proof and never current state. Core consumes `item_states` as live truth, lets plan-wide `contract_quarantined` override accepted ACKs, preserves terminal decisions/reasons, and reconciles terminal no-execution outcomes into non-active Core rows. Known pending/working states remain retryable, `completed_no_trade` uses the entry reason ahead of non-applicable protective siblings, and unknown future statuses remain `unknown` rather than accepted.
- In dispatch mode the background runner pre-dispatches eligible next-open plans to exec during `PREOPEN` at/after 08:00 KST, then refreshes the core-owned exec read model during `OPEN` instead of submitting local next-open or intraday auto-sell orders from core. This avoids duplicate live actions while preserving explicit operator visibility in core, and it keeps short-term trigger/chase entries in a pending/configuration-safe dispatch lane rather than unsafe market-order translation.
- `GET /execution/runtime/status`, `GET /execution/runtime/monitored-symbols`, `GET /execution/runtime/daily-board`, and `GET /execution/runtime/symbols/{symbol}` are the dashboard read-model routes for Web. Their canonical UI statuses, monitoring states, freshness states, row keys, and today-activity shape are defined by `execution_handoff_contract.py` and summarized in [docs/CORE_API_SPEC.md](./CORE_API_SPEC.md#5-execution-handoff--runtime-contract). Daily-board `activity_coverage` distinguishes `no_activity` from `unavailable`; when Exec reports current activity but Core has no materialized rows, the board remains empty only with `status_reason=exec_activity_not_materialized` and `freshness.status=unavailable`.
- `GET /execution/runtime/monitored-symbols` also publishes validated prior-session signal-decider WAIT symbols as the explicit `realtime_subscription.observation_only_symbols` subset. Those rows are price-observation only (`signal_wait_observation_only`) and carry no plan, handoff, trigger/chase, target/stop, job, or order authority; existing holdings and live Exec membership retain their stronger runtime classification.
- The execution runtime dashboard rows now include a compact display price read model: `current_price`, `price_as_of`, `price_received_at`, `price_source`, `price_status`, `display_price_available`, `realtime_subscribed`, and `realtime_subscription_reason`. Source priority is realtime websocket tick, then recent local quote cache/current-quote cache, then recent daily close. Cache/daily fallbacks are labeled as `fallback` or `stale` instead of `unavailable`; capacity-limited symbols keep `realtime_subscription_reason=capacity_limited`. These fields never trigger browser-side KIS access or request-time KIS REST quote fan-out.

## EOD freshness read-layer notes
- Canonical semantics live in `docs/EOD_STATUS_SEMANTICS_CONTRACT.md`.
- `GET /eod/freshness` is the compact web-facing read API for EOD ingestion freshness.
- The response now also includes a top-level `market_session` block so web and operator consumers can distinguish the requested/current calendar date from the latest valid trading date and can label weekend, holiday, and after-close freshness without ambiguous "current cycle" wording.
- It reports the current Seoul trade date, today's stage-specific status for price, technical analysis, action summary, and fundamentals, plus the latest stored dates for price bars, technical snapshots, and action summaries.
- `today.trade_date` is the current Seoul calendar date from `server_time[:10]`; weekends, holidays, and other break-days do not backshift `today` to a previous trading day.
- Today's price, technical-analysis, and action-summary stage totals are based on the current active symbol universe. Their succeeded counts come from same-day persisted rows for active symbols; once a stage has same-day rows, failed counts represent active symbols still missing that persisted data.
- `today.fundamentals` is explicitly an activity view. Its `basis` is `same_day_snapshot_updates`, so `symbols_succeeded` counts distinct stock codes with DART fundamentals snapshots updated during the current Seoul day and `symbols_failed` counts distinct financial-report stock codes whose capture attempt failed that same day.
- `today.fundamentals.current_run` is the latest persisted DART fundamentals refresh run for the current `market_date` when one exists. It is sourced from `dart_fundamentals_refresh_runs` and keeps refresh progress visible even when same-day snapshot updates are still zero. A running current-day refresh run overrides `today.fundamentals.status` to `running`, but a completed same-day no-op refresh still leaves the stage `missing` if no same-day snapshot updates exist.
- The `latest` block preserves `price_trade_date` plus the legacy `symbols_*` fields and now also mirrors its web-facing summary at top level through `latest.trade_date`, `latest.updated_at`, `latest.succeeded`, `latest.failed`, and `latest.total`.
- `latest.summary.basis` explicitly names the summary basis. `latest_eod_run_symbol_universe` means counts come from the selected `eod_collection_runs` row for `latest.trade_date`; `stored_price_bars_for_latest_trade_date` is the fallback when stored price bars exist but no matching EOD run row is available, in which case `total == succeeded` and `failed == 0`.
- If a newer same-date retry covers fewer symbols than the stored price-bar population, freshness prefers a more complete same-date run by total or success count. A 1-symbol retry delta therefore cannot replace a representative 2,679-symbol daily summary.
- `latest.updated_at` comes from the latest run's `run_metadata.last_progress_at` when available, otherwise from its run timestamps; the stored-price-bar fallback uses the max `daily_price_bars.captured_at` for `latest.trade_date`.
- `latest.eod_status` falls back to all stored price bars for `latest.price_trade_date`, including symbols that are no longer in the current active universe.
- `latest.fundamentals` is the latest-available fundamentals coverage view. It is sourced from the latest completed or partial `dart_fundamentals_refresh_runs` row across market dates, so weekends, pre-close periods, and same-day no-op refreshes do not collapse fundamentals availability back to zero.
- In `latest.fundamentals`, `symbols_total` is the selected refresh-run universe (`run_metadata.symbols_selected` when present, otherwise the stored row total), `symbols_checked` is the number processed by that run, `symbols_succeeded` is `symbols_fresh + symbols_refreshed`, and `symbols_refreshed` is preserved separately as the count of symbols whose fundamentals were newly updated in that run.
- `today.pykrx_enrichment` and `latest.pykrx_enrichment` expose persisted `daily_pykrx_enrichment_rows` coverage by category, including expected/present row counts, missing categories, and partial categories. This keeps investor-flow, short-selling, sector, market-breadth, and valuation coverage visible on the compact operational freshness surface.
- The `today` block is scoped only to the current Seoul trade date; previous-day historical availability is surfaced through `latest.*`, not copied into `today.*`.

## EOD pipeline status notes
- Canonical semantics live in `docs/EOD_STATUS_SEMANTICS_CONTRACT.md`.
- `GET /eod/pipeline/status` is the operator-facing live status API for the post-close EOD pipeline. Its default read is polling-safe: expensive row-count missing diagnostics, PyKRX enrichment coverage scans, and feedback-run context are omitted unless `include_diagnostics=true` and/or `include_feedback_context=true` is passed.
- It stays separate from `GET /eod/freshness`: freshness answers whether the stored data is available, while pipeline status answers which stage is running now and what work is currently in progress.
- The payload now also includes both `market` and `market_session` blocks. `market` reflects the current exchange clock state, while `market_session` reflects the semantics of the requested `market_date`, including the latest valid trading date and whether quote or intraday data should be expected for that date.
- With no `market_date`, the route uses the market date from the actual latest persisted official daily run. If no official run exists it falls back to the current Seoul calendar date; an explicit date always wins.
- The route reads official durable `daily_pipeline_runs` / `daily_pipeline_stage_runs` state first, merges same-date historical official stage rows when the latest run is a resumed subset, then falls back to existing `eod_collection_runs`, DART refresh runs, and persisted output inference for stages with no official stage row.
- Automatic `/eod/pykrx/daily/run-if-due` runs now create official daily pipeline run state and keep it open until chained follow-ups finish or fail. If an active auto run has no official rows, the status route promotes non-PyKRX follow-up entries from `eod_collection_runs.run_metadata.stage_progress` so `running_stages`, `current_stage`, timestamps, source run IDs, and stale-running threshold metadata remain visible.
- A stored child stage that still says `running` after its official parent is terminal is rendered as `interrupted` with orphan diagnostics and is excluded from `running_stages`. PyKRX diagnostic coverage fields remain authoritative over stale official detail overlays, so completed category/gate coverage and warnings cannot regress to `waiting` in the read model.
- The current pipeline payload represents the canonical chain from `master_refresh` and `price_collection` through external news, `macro_context_refresh`, `agent_feedback_summaries`, `signal_decider`, and `signal_decider_evaluations`.
- The scheduled PyKRX daily stage sequence includes `pykrx_enrichment` immediately after `price_collection` and before technical snapshots. The stage must populate `sector_classification`, `investor_flow_symbol`, `short_selling`, and `valuation_snapshot` to their category-specific readiness thresholds before downstream exec/decider use is allowed.
- Direct `market_risk_filter` API and CLI runs create official run state and checkpoint KIS fetch progress before result rows are persisted. Stage-orchestrated DART fundamentals and agent-feedback retry stages also publish their native progress checkpoints into the official daily stage rows.
- `signal_features`, `external_news_collect`, `external_news_enrich`, `macro_context_refresh`, and `signal_decider` infer availability from persisted `daily_signal_features`, point-in-time `external_news_item_symbols` associations, append-only versioned `external_news_item_classifications` sidecars, `macro_context_observations`, `agent_context_feedback`, and `signal_decider_decision_snapshots` rows. External-news enrich completion is based on the current `CLASSIFIER_VERSION` plus the material/noise/source-status contract (`materiality`, `materiality_reason`, `event_type`, `access_status`, and `source_evidence`); older sidecars are reported as outdated/legacy and cannot make the current enrich stage ready. Daily enrichment admits an article missing the current classifier version when either the article is in the normal recency window or its requested-symbol association falls in the half-open Seoul market-day window; the current-day upper bound is frozen at invocation time. A resumed run that only contains `signal_decider_evaluations` must not make those same-day persisted outputs look pending.
- Omitted dates on `POST /eod/pykrx/backfill` and `POST /eod/pykrx/daily/run-if-due` resolve to the latest KRX trading session. Explicit weekend or holiday dates return HTTP 400 before PyKRX collection starts.
- `master_refresh` and `pykrx_universe_refresh` are pre-open/global stages. When same-date downstream output exists but those global stages have no stage row, they are reported as `skipped` with a reason instead of becoming the misleading current actionable stage.
- When diagnostics are requested, `pykrx_enrichment` reads persisted `daily_pykrx_enrichment_rows` coverage for the requested date and overlays live PyKRX run metadata when the scheduled stage is running, partial, or failed before rows are fully visible. It reports per-category completion across sector classification, breadth, investor flow, short-selling, valuation snapshot, and foreign ownership slices, plus progress extras such as downstream preflight status and failed categories when present. Its execution/storage status stays separate from decider gate readiness through stage-level `gate_status` fields and top-level `gate_summary`.
- With diagnostics enabled, row-count-derived stages such as `market_risk_filter` expose `missing_count`, `missing_symbols_sample`, `coverage_ratio`, `gate_status`, `severity`, and `blocking_status` diagnostics when stored rows do not cover the same-date price-bar universe. If active feedback is running with zero failures and the missing `market_risk_filter` rows are outside that run's requested symbol scope, Core reports the row gap as `severity=degraded`, `blocking_status=non_blocking`, and `gate_status=ready` while keeping the missing symbols visible.
- When a same-day agent feedback run is active, `GET /eod/pipeline/status` reflects it under `agent_feedback_summaries` from `agent_context_feedback_runs` or runtime feedback state even when no official daily pipeline stage row exists. This lets dashboards distinguish active feedback progress from non-blocking upstream coverage gaps and from feedback failures or stalls.
- `agent_feedback_summaries` reconciles stale durable run snapshots against persisted child feedback/failure rows before rendering status. Its `updated_at` follows the latest successful or failed child activity, and `details` includes active roles, target/completed/failed symbol counts, role-level progress, latest successful feedback timestamp, and latest failed feedback timestamp when present.
- The durable feedback fallback prefers the latest canonical daily retry parent before considering legacy or child runs, so a newer narrow child cannot replace the full cohort in the operator status. Role-level pending work prevents a false `completed` stage.
- Official stage result summaries retain compact operational aggregates but omit nested bulk evidence collections on write and read. `details.result_summary_omissions` records each removed path and size so historical oversized payloads remain explainable without returning tens of megabytes.
- Decision-stage history separates overlay eligibility from completion authority. Replacing a timestamped competing state requires a strictly newer same-lineage stage row; undated or generic `pending` placeholders and diagnostic `partial` / `blocked` / `waiting` history follow the narrower fallback rules. Regardless of overlay eligibility, `signal_decider` and `signal_decider_evaluations` rows with a stored `result_summary` can establish `completed` only after passing their stage-specific semantic proof, even when their outer counts are exact; explicit skips, `triggered=false`, incomplete or malformed payloads, failures, and warning-bearing completion claims fail closed and render as `partial`. A newer unrelated run that omits those stages does not erase an older proven completion. The detailed compatibility and proof rules live in [docs/EOD_STATUS_SEMANTICS_CONTRACT.md](./EOD_STATUS_SEMANTICS_CONTRACT.md).
- Those same PyKRX enrichment slices are joined into `GET /agent-context/symbol-day` under `pre_decider_enrichment_context.flow_short_sector_context`, and `valuation_snapshot.trading_value` is the preferred raw trading-value source for decider handoff.
- While a pykrx run is `running`, the inferred current stage is authoritative for live display: that stage remains `running`, later pykrx stages stay `pending` until they actually start, and stale `stage_progress.status=running` entries must be downgraded once the owning run is no longer running.
- Factor stages are derived from same-day stored result-row coverage instead of dedicated run rows. A default-selected factor stage with no stored rows for the requested market date remains `pending`, so the overall pipeline must stay `partial` until those rows exist.
- Stage payloads include normalized status, timestamps, processed or total or failed counts where available, current step or activity text, and linked source run IDs so operators can correlate the live run with existing inspect routes.

## EOD pipeline stage orchestration notes
- `GET /eod/pipeline/stages` is the operator-facing stage catalog for the explicit daily pipeline orchestrator.
- The catalog exposes the canonical stage order, the default daily run sequence, per-stage dependency metadata, supported inputs, inspect routes, and output-table hints.
- The default daily run now includes the PyKRX enrichment stage immediately after `price_collection`, then the factor/scoring sequence after DART fundamentals and Piotroski: `momentum_factors`, `value_factors`, `low_risk_factors`, `beta_factors`, `advanced_value_factors`, `unified_value_factors`, `quality_factors`, and `composite_factors`.
- The valuation dependency contract is explicit: `piotroski_filter` requires fundamentals plus PyKRX enrichment; `value_factors` requires price collection plus enrichment; `advanced_value_factors` and `unified_value_factors` require price collection, enrichment, and fundamentals; `quality_factors` requires price collection plus fundamentals.
- `POST /eod/pipeline/run` executes an explicit stage subset in canonical order while reusing the underlying stage operations rather than duplicating orchestration logic. Background requests validate stage names and `market_date` before returning `202`; invalid input returns the same `400` behavior as synchronous execution. Admission deduplicates against every active run for the same `market_date`, including a non-overlapping stage subset. Timestamp age is diagnostic evidence only: ownership transfers only during startup reconciliation or when a new automatic worker holds the same provider advisory fence and proves every active row is a stale automatic lineage. Long synchronous factor stages refresh only their run/stage timestamps through short isolated heartbeat writes.
- An explicit prior `market_date` on `POST /eod/pipeline/run` uses the `manual_api` recovery boundary automatically. Current-only stages (`master_refresh`, `pykrx_universe_refresh`, `signal_features`, fundamentals refresh, external-news collect/enrich, macro refresh, and intraday snapshots) return HTTP 200 `point_in_time_recovery_current_only_stage` safe-skip results instead of reading live data or writing historical rows. The two market-risk stages do the same except for the immediately previous KRX trading session during the current trading day's `PREOPEN`; in that bounded window they may call KIS and persist snapshot/filter rows for the previous session. Older dates and all prior-date requests from `OPEN` onward still safe-skip.
- If the recovered date's next-open action window has passed, feedback summaries, signal decider, decider evaluations, and the next-open execution plan return `next_open_window_expired`. These results are auditable no-ops and do not create historical decisions or plan items.
- Requested stages are reordered to the canonical sequence before execution. The response preserves both `requested_stages` and `resolved_stages` so operators can audit what was asked for versus what ran.
- `resume_from_stage` starts at that canonical stage and preserves upstream outputs by not rerunning earlier stages.
- The route does not silently inject missing dependencies. Callers can inspect `depends_on` from the catalog and choose whether they want a narrow rerun or a wider prerequisite-inclusive slice. A narrow `agent_feedback_summaries` or `signal_decider` recovery is admitted only when omitted same-date persisted structural prerequisites, including `signal_features`, are already ready; prerequisites included earlier in that same recovery are checked after they execute and immediately before feedback. `bypass_prerequisite_gate` cannot bypass those data dependencies and applies only to softer feedback-service retry gates after structural readiness. External-news collect/enrich and macro refresh remain ordering-only optional context: a terminal degraded attempt may reduce confidence but does not become a hard feedback gate. Persisted ordering evidence still matters: if factors, signal features, or completed optional context are newer than feedback, the affected suffix is replayed with feedback reuse disabled.

## Piotroski filter read-layer notes
- `GET /eod/piotroski-filter-results` is the persisted read API for `daily_piotroski_filter_results`.
- `market_date` is optional. When omitted, the route resolves the latest stored Piotroski result date for the current request scope. When `symbol` is provided, latest-date resolution is scoped to that symbol; without `symbol`, it is scoped to the full stored result set.
- When a specific `market_date` is requested, the read path preserves the exact date when rows exist for that scope. If no rows exist for the requested scope and date, it falls back to the latest stored date on or before the requested date and reports that resolution explicitly.
- The read path intentionally returns both passed and not-passed rows because the DART daily fundamentals refresh stores one persisted result per evaluated symbol, not just the winners.
- The persisted Piotroski table is one half of agent-feedback eligibility. Symbol-level agent feedback on a `market_date` now requires both `daily_piotroski_filter_results.passed_filter=true` and `daily_market_risk_filter_results.passed_filter=true`.
- Computation selects the latest two available successful annual snapshots received on or before the market date. Within each year the newest filing wins, with `CFS` preferred only when the same filing has both `CFS` and `OFS`; a newer corrected `OFS` therefore cannot be hidden by an older `CFS`. Canonical stored ratios are preferred; debt, current, gross-margin, and asset-turnover ratios are derived from raw highlights when needed. Real annual-report capture persists the audit opinion before the financial snapshot and marks the event captured only after both succeed. Piotroski selects only captured-event snapshots and accepts audit evidence with the selected current filing's exact `rcept_no`; missing or unparseable evidence remains retryable and fail-closed instead of reusing an older clean opinion.
- A Piotroski pass requires all eight financial signals to be available and a raw nine-point score of at least seven. The event-derived `no_new_share_issuance` signal remains optional until full-period disclosure coverage can prove that an absent row means no issuance; missing evidence receives no point and never shrinks the nine-point denominator. `required_financial_signal_coverage_ratio`, `signal_coverage_ratio`, and `missing_optional_signal_names` expose the distinction. Debt-ratio signals additionally require positive equity so capital impairment cannot rank as low leverage.
- Results are ordered with passed names first, then lower PBR percentile ranks first, so callers can consume the returned list directly without applying a second client-side sort.
- The response keeps `market_date` as the resolved result-set date for compatibility and now also includes `requested_market_date`, `resolved_market_date`, `latest_mode`, `is_latest_fallback`, and `fallback_policy='latest_on_or_before_requested_market_date'` so callers can distinguish exact reads, latest-mode reads, and requested-date fallback behavior.
- The `summary` block reports the number of returned entries, passed vs not-passed counts, and any requested symbol that did not have a stored row for the resolved date.

## Low-risk factor notes
- `daily_low_risk_factor_results` is the persisted low-volatility and downside-risk layer keyed by `symbol_id + market_date`.
- `POST /eod/low-risk-factors/compute` rebuilds the persisted rows from stored `daily_price_bars` only; it does not pull live quotes or execution data.
- `GET /eod/low-risk-factors` is the persisted read API for that table. When `symbol` is provided, the route returns a single `item`; without `symbol`, it returns ordered `items` for the requested date.
- v1 realized volatility uses simple close-to-close daily returns from stored `close_price`, with 60-return and 120-return trailing windows annualized by `sqrt(252)`.
- v1 downside risk uses trailing 120 stored closes for `max_drawdown_120d`, expressed as the worst `close / running_peak - 1.0` value inside that window.
- v1 liquidity support uses `avg_trading_value_20d` from exactly the trailing 20 stored trade-date bars and never replaces invalid recent turnover with older observations. Positive-volume zero or missing turnover invalidates the window, while a true zero-volume bar contributes zero. Non-positive 20-day averages are excluded from liquidity ranking, then a cross-sectional liquidity-percentile floor prevents thinly traded names from being classified as safe by low volatility alone.
- Cross-sectional percentiles are stored with `best_symbol=1.0` and `worst_symbol=0.0`; v1 uses deterministic symbol ordering to break ties.
- The combined v1 low-risk score is explicit and persisted: `0.30 * volatility_60d_percentile + 0.30 * volatility_120d_percentile + 0.25 * max_drawdown_120d_percentile + 0.15 * liquidity_percentile`.
- `is_low_risk_eligible` requires the liquidity floor to pass and the combined score to meet the stored eligible threshold. Rows with incomplete history remain persisted with partial raw metrics, `low_risk_score=null`, and `low_risk_classification=insufficient_history`.

## Advanced value factor notes
- `daily_advanced_value_factor_results` is the DB-backed advanced-value layer keyed by `symbol_id + market_date`, and it intentionally sits alongside `daily_value_factor_results` rather than replacing value v1.
- `POST /eod/advanced-value-factors/compute` rebuilds persisted rows from stored `daily_price_bars`, same-day stored PyKRX valuation enrichment, and stored DART fundamentals snapshots only; it does not call live quote, broker, or execution paths during the request.
- `GET /eod/advanced-value-factors` is the persisted read API for that table. When `symbol` is provided, the route returns a single `item`; without `symbol`, it returns ordered `items` for the requested date.
- `advanced_value_v1` uses the latest successful stored annual DART snapshot whose receipt date is on or before the requested `market_date` (`report_code=11011`, `period_type=annual`). It selects the latest filing in the latest business year and prefers `CFS` only within the same filing, so a newer corrected `OFS` wins over an older `CFS`.
- The loader always reads the small set of relevant DART statement rows in bounded snapshot-ID chunks, including for a full-market universe. Canonical cash-and-cash-equivalents highlights are preferred, with matched statement rows retained as the fallback; CAPEX and depreciation/amortization continue to use filtered statement rows so existing snapshots remain computable without a backfill.
- `fcf_yield` is defined as `free_cash_flow / market_cap_proxy`, where `free_cash_flow = operating_cash_flow - capex` and the first-pass capex proxy is the sum of matched PPE and intangible-asset acquisition cash outflows.
- `ev_to_ebitda` is defined as `enterprise_value / ebitda`, where `enterprise_value = market_cap_proxy + total_liabilities - cash_and_cash_equivalents` and `ebitda = operating_income + depreciation_and_amortization`.
- `market_cap_proxy` first uses the positive observed `market_cap` from the same-day direct PyKRX `valuation_snapshot`. Only when that row is unavailable does it fall back to `pbr * total_equity` using the same-day stored bar and selected annual DART snapshot; the chosen source is retained in `factor_payload`.
- Higher `fcf_yield` ranks better and lower `ev_to_ebitda` ranks better. Cross-sectional percentiles are stored with `best_symbol=1.0` and `worst_symbol=0.0`.
- The combined `advanced_value_score` is the equal-weight mean of the two component percentiles and requires both component metrics to be valid for scoring. Rows with only one valid metric remain persisted with `advanced_value_score=null` and `advanced_value_classification=insufficient_components`.
- Negative free cash flow remains a valid but unattractive `fcf_yield` input. Non-positive EBITDA and non-positive enterprise value are treated as explicit invalid EV/EBITDA cases rather than ranked values.
- Auditability is explicit in `factor_payload`: the stored row keeps the selected annual snapshot metadata, matched DART input rows/highlights, component status flags, methodology assumptions, and the raw numerator/denominator pieces used to derive the final metrics.
- For shell-driven operations, use `python3.11 -m app.internal.ops eod-advanced-value-factors-compute --market-date YYYY-MM-DD` from `apps/api`.

## DART pipeline notes
- Practical lower bound for `fnlttSinglAcntAll` and `list.json` in this pipeline is 2015 onward. Open DART documents both the filing-search date range and the financial-statement `bsns_year` support as 2015 and later, so the DB `daily_price_bars` minimum of `2007-06-05` does not expand the usable fundamentals backfill window.
- Ongoing machine-DB sync now persists only periodic financial-report events. Non-financial disclosures are still fetched from Open DART during polling, but the financial-report path is the one the capture and history workflow depends on.
- `GET /disclosures/dart/fundamentals` and `GET /disclosures/dart/fundamentals/history` now expose `fundamental_context` alongside the raw statement/highlight payloads. That normalized block groups canonical BS/IS/CF facts, keeps missing-account handling explicit, derives common profitability, leverage/liquidity, and cash-flow quality metrics, and preserves receipt/report/fs-div/source metadata for downstream agents.
- The current-universe backfill operator is intentionally batch-oriented. Use the current active symbol universe only, slice with `symbol_limit` and `symbol_offset`, sync only the relevant financial report events for that slice, then capture only those symbols' pending or failed fundamentals.
- Fundamentals capture treats `pending` and `failed` disclosure events as retryable. A `CFS` financial-statement `[013]` response retries the same request as `OFS`; only a final `[013]` response after that fallback becomes terminal `no_data`. Non-`000` responses and nominal successes with no statement rows are rejected before snapshot replacement, so an empty or error payload cannot overwrite a usable snapshot. Filing/request inference problems remain terminal `mapping_failed` so normal daily retries do not re-hammer them.
- For operator-driven continuation batches, prefer `python3.11 -m app.dart.backfill_current_universe ...` or a quoted `curl` URL. Unquoted shell query strings can turn `?` and `&` into zsh parsing issues before the request reaches the API.
- For unattended full-universe continuation, use `python3.11 -m app.dart.backfill_current_universe_runner ...`; it is the repo-owned long-run path with per-batch log-file progress and failure offsets.
- Daily incremental fundamentals refresh is the EOD-style steady-state operator path. It reads each selected active symbol's latest resolved DART fundamentals receipt date, syncs only that symbol's newer DART financial-report disclosure window, captures only stale or missing symbols' exact pending/failed event IDs, records a high-level `dart_fundamentals_refresh_runs` row for inspection, and then rebuilds persisted `daily_piotroski_filter_results` for that market date so both passed and not-passed symbols are stored. Corporation sync errors are isolated per corporation and make the sync/refresh `partial` or `failed` instead of being reported as completed. Three consecutive systemic transport/provider failures trip a circuit breaker, retain the remaining corporations as unattempted retry scope, and stop a global outage from becoming a many-hour serial loop; corporation-specific lookup failures do not count toward that breaker. Manual backfill also stops on an incomplete batch without advancing its resume offset. Normal runs apply `capture_limit` and remain partial while retryable events are left. Explicit `force=true` instead processes the full selected symbol/date scope without a capture limit, because forced candidate selection has no durable event cursor; use `symbol_limit` to bound forced work. When initial backfill is disabled, symbols with no fundamentals are checked through a deterministic rotating daily probe bounded by `DART_FUNDAMENTALS_DAILY_MISSING_SYMBOL_PROBE_LIMIT`; unselected missing symbols remain explicitly deferred.
- `GET /disclosures/dart/fundamentals/daily/inspect` now exposes the run-scoped cycle-day updated-company activity directly through `updated_entries_summary`, `updated_entries_preview`, and `updated_entries`. That surface is intentionally separate from latest-coverage semantics: `symbols_refreshed` and `updated_entries_summary.updated_count` answer “which symbols were updated during this refresh cycle,” while latest available fundamentals coverage remains a separate read concern.
- `updated_entries` returns one primary entry per updated symbol for the selected refresh run. The current deterministic category contract is: `initial_fundamentals_capture` when the symbol had no stored fundamentals before the run, and `financial_statement_refresh` when the symbol already had stored fundamentals and the cycle captured a newer filing.
- `updated_entries_preview` is the first three items from the full updated list, and `updated_entries_summary` includes `visible_preview_limit`, `visible_preview_count`, `has_more`, and `remaining_count` so the dashboard can render `first 3 + More` without inferring preview state from unrelated counters.
- Daily refresh and backfill responses include `operator_buckets` for lookup/mapping errors, retryable capture failures, terminal no-data events, terminal mapping failures, and remaining retryable events. `GET /disclosures/dart/fundamentals/capture/inspect?capture_status=no_data` can be used to inspect terminal no-data events directly.
