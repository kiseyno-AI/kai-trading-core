# GET /trading/orders/next-open-execution and POST /trading/orders/next-open-execution/run-if-due

## Summary
Inspect or execute the persisted next-open buy plan derived from the latest previous-trading-day decision snapshots. The planner now includes both classic `signal-decider` next-open buys and actionable `short-term-decider` tactical candidates, stores blocked-vs-eligible validation results durably with explicit decider identity, and the submit hook either reuses the existing trading-order persistence flow or, when `SIGNAL_DECIDER_EXEC_INTEGRATION_MODE=dispatch`, translates eligible rows into normalized exec plan items and delegates sizing/execution authority to `kai-trading-exec`.

For dispatch-mode buy candidates, core sends sizing context as a candidate contract (`quantity_policy.type='exec_agent_sized'`) so exec can make final share decisions using account/feedback/context rails, budgets, reference/entry context, confidence, and target/stop metadata. Core-local disabled mode keeps the legacy fixed-share signal-decider submit path.

Short-term validation now preserves the decider request's `pre_decider_enrichment_context` in both `validation.pre_decider_enrichment_context` and `validation.short_term.pre_decider_enrichment_context`. Operators can inspect the quote/orderbook snapshot status, raw-vs-estimated trading value provenance, investor/short-selling flow, and sector-peer context that were available before dispatch validation.

Short-term validation and traceability also preserve signal-decider alignment audit fields. Same-symbol `WAIT` conflicts are classified as `wait_conflict_block` or `wait_conflict_override`; the default live mode is report-only, so `alignment_gate_action="report_only_block_candidate"` records the candidate gate without vetoing the row. The linked signal-decider snapshot id is exposed as `alignment_signal_decider_decision_snapshot_id`.

Validation now also preserves `decision_input_quality_context` for both `signal-decider` and `short-term-decider` rows. This reusable quality-provenance envelope separates data quality, market/setup edge, execution feasibility, and final buy-quality judgment. Stale or fallback quote snapshots and missing raw source turnover appear as hard blocks or major discounts in the envelope; empty news remains neutral secondary context. The envelope is informational in core-local validation and is passed to exec for account-aware sizing/risk decisions in dispatch mode.

Validation and exec handoffs also preserve `market_regime_context` for buy-oriented rows. The payload is generated by core from PyKRX market breadth, sector/category peer context, and market-relative strength, with `posture`, `recommended_exec_action`, `recommended_sizing_multiplier`, freshness/source metadata, and explicit missing fields. In dispatch mode it is copied to `risk_context.market_regime_context` and `risk_context.decider_handoff_context.decider_input_context.market_regime_context` so kiseyno-AI/kai-trading-exec#140 can enforce market/sector guardrails without querying core.

Before planning, local submit, or exec dispatch proceeds, Core checks source-market-date PyKRX enrichment coverage for `sector_classification`, `investor_flow_symbol`, and `short_selling`. If any required category is missing or effectively zero coverage, classic `signal-decider` immediate next-open buys are blocked with `reason="pykrx_enrichment_preflight_blocked"` and no local signal-decider order is submitted unless `force=true` is supplied. Actionable `short-term-decider` watch rows are still materialized when candidate-level trigger/chase fields exist; the preflight failure is attached as degraded warning metadata so operators can distinguish “watch candidates exist but are degraded” from “no candidates exist.”

Requested `target_trade_date` values are normalized to the next KRX open date on or after the request date using the shared KIS `chk-holiday` calendar. Live local submission, intraday auto-sell submission, and exec dispatch fail closed when calendar truth is only available from fallback metadata; `force=true` is the operator override.

In exec-dispatch mode, watcher candidates are not blocked solely because `data_quality_warnings` are present. Core carries those warnings into the validation and exec handoff so the exec-side account-aware agent can make the final sizing/risk decision. Short-term tactical rows are still blocked when required trigger/chase/target/stop levels are missing, when the latest available reference price is already above the chase limit, or when the decision-input quality envelope emits hard blocks.

When short-term candidates are present but `SIGNAL_DECIDER_NEXT_OPEN_ACCOUNT_TARGETS` is empty, rows are still materialized with an explicit synthetic routing rail:
- `account_reference = KIS:00000000-00`
- `account_label = UNSPECIFIED_ROUTE`
- `allocation_mode = unspecified_route` in traceability/risk context

In that case the synthetic rail is treated as a budget/route placeholder, not a hard pre-priced share budget.

## Contract source
When the POST route delegates to Exec, the serialized dispatch payload is validated by `apps/api/app/orders/execution_handoff_contract.py` as `signal_decider_exec_plan_v2`; nested decider handoff context is validated as `exec_agent_decider_handoff_v1`. Core owns strategy context and payload construction, while Exec owns acceptance, sizing, and order/execution truth.

## Example request
```http
GET /trading/orders/next-open-execution?target_trade_date=2026-04-30&refresh=true
```

```http
POST /trading/orders/next-open-execution/run-if-due
Content-Type: application/json

{
  "target_trade_date": "2026-04-30",
  "dry_run": false,
  "force": false
}
```

Signal-decider rows keep the existing market-open submit behavior only in core-local mode. `short-term-decider` rows are only mapped when the tactical action is actionable (`scalp_buy_candidate` or `watch_for_trigger`) and all required guarded-entry levels pass. `scalp_buy_candidate` exposes `handoff_intent="tactical_buy"` with `entry_execution_mode="guarded_tactical_buy"`, while `watch_for_trigger` exposes `handoff_intent="intraday_watch_buy"` with `entry_execution_mode="pending_trigger_limit"`. In core-local mode they remain planned-only because trigger/chase semantics are not translated into live market orders locally. In exec dispatch mode, both signal and short-term entry legs are sent at/after 08:00 KST as exec-agent-sized candidates; accepted rows without an agent-approved positive quantity move to `execution_status="delegated_for_exec_agent_sizing"`, and the delegated linkage or audit state is stored under `submission.exec_dispatch` for each item, including decider-aware `plan_id`, remote item ids, last dispatch attempt, and the latest matched readback snapshot.

When the enrichment preflight blocks, the response keeps the same top-level shape with empty dispatch/submission counts, `summary.reason="pykrx_enrichment_preflight_blocked"`, `enrichment_preflight.allowed=false`, and per-row validation details under `validation.pykrx_enrichment_preflight`. Signal-decider rows receive a blocking reason; short-term watch rows remain visible as conditional candidates and receive a warning/degraded reason.
